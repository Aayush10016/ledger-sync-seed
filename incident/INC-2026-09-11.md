## Incident Report Update

**Root Cause:** The transaction amount regex in `Amounts.java` strictly required decimal places `(?:\.\d{1,2})`. Because integer amounts like "Rs.5" lacked decimals, the regex engine rejected them, forcing the parser to silently grab the next available decimal number in the message (which happened to be the Available Balance of `Rs.92,213.10`).

**Contributing Factors:**
1. **Test Coverage Gaps:** `AmountsTest.java` only tested decimal-formatted amounts, ensuring the test suite remained green despite the logical flaw for whole-rupee transactions.
2. **Silent Fallback Logic:** The parser allowed silently advancing to the next available decimal number when the primary amount match failed, swapping the transaction amount with the balance instead of failing explicitly.

**How we found it:** `incident/app.log` showed the parser rejecting `Rs.5`, and substituting it with `Rs.92,213.10`.
**Who was affected:** Exactly 38 messages in `fixtures/corpus-a.jsonl`: supported bank transaction messages where the first rupee value was a whole-rupee transaction amount and a later available balance or card limit contained decimals.
**Why it cannot happen again:** The regex in `Amounts.java` has been updated to make the decimal block `(?:\.\d{1,2})?` optional.
**Prevention:** We added robust integer testing to `AmountsTest.java` and separated balance parsing to prevent unintentional cross-matching.
## Five-line Incident Note

1. Integer rupee transaction amounts such as `Rs.5` were skipped, so the parser could read the later available-balance amount instead.
2. The issue was reproduced from `incident/app.log`, `V2__seed.sql`, and the water-can SMS shape.
