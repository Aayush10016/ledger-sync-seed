## Incident Report Update

**What broke:** The amount regex in `Amounts.java` strictly required decimal places, causing it to skip integer amounts like "Rs.5" and silently grab the next available decimal number (the Available Balance).
**How we found it:** `incident/app.log` showed the parser rejecting `Rs.5`, and the `fallback` logic parsing `Rs.92,213.10` instead.
**Who was affected:** Any transaction where the bank reported the transaction amount as a whole integer without decimals (e.g., Rs.5, Rs.10).
**Why it cannot happen again:** The regex in `Amounts.java` has been updated to make the decimal block `(?:\.\d{1,2})?` optional, preventing fallback on integer amounts.
**Prevention:** We added robust integer testing to `AmountsTest.java` which previously only tested decimal-formatted amounts.

## Five-line Incident Note

1. Integer rupee transaction amounts such as `Rs.5` were skipped, so the parser could read the later available-balance amount instead.
2. The issue was reproduced from `incident/app.log`, `V2__seed.sql`, and the water-can SMS shape.
3. Affected users were those whose bank sent whole-rupee transaction amounts before an available-balance field.
4. Root cause was the transaction amount regex requiring decimal places while balance values usually had decimals.
5. The fix accepts integer transaction amounts and keeps balance parsing separate, with regression coverage for `Rs.5` plus `Avl Bal`.
